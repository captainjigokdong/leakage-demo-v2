### D6 "지금 설계가 옳다"의 근거 (조건 E)

- 설명서 `person_links.person_id`: 값이 알려지는 때 = **자료 추출 시** 연결. tp에는 같은 사람의 다른 등록 번호를 알 수 없다.
- 점검기 원리 시험 `q1_history_person`: `history_key=person_id`는 Q1 차단 (3단계, 사례와 무관한 원리).
- 3b 검수 R3: 에이전트의 수정안(`person_id`)이 Q1 차단에 걸렸다.
- 1회차 에이전트 7명 중 5명이 같은 이유로 "설계가 맞다"고 판단했다 (가정).
- 결과는 `match_key=person_id`로 찾는다. 결과는 tp 뒤에 정해지므로 추출 때의 연결을 써도 tp에 알 수 없는 정보를 특징에 쓰는 것이 아니다.

## 분류 원칙 (2026-10-05 사용자 지시)

- 지적마다 **사실인가**(설계서·설명서·데이터로 확인), **고칠 수 있는가**(형식 안에서, 데이터를 바꾸지 않고)로 나눈다. 에이전트가 붙인 kind(문제·가정·점검 불가)와 상관없이 같은 기준을 쓴다.
  - 사실이고 고칠 수 있음 → **고침** (칸을 고치거나, 오해가 생긴 곳은 서술로 명시)
  - 사실이고 고칠 수 없음 → **정당한 지적 목록 후보**
  - 사실이 아님 → **사실 아님** (그대로 둠)
- "지금 설계가 옳다"로 목록에 넣는 것은 **서술로 오해를 없앤 뒤에도 남는 것만**이다. 점검기 경고(K1)도 같은 기준이다.
- 목록은 좁게 둔다. 목록에 오른 칸과 결함 대상 칸이 겹치면 결함 대상이 우선한다 (채점은 5단계).
- **D7(병동 × 기간 측정 빈도)은 서술로 고쳤다. 2회차에서 다시 지적되면 목록이 아니라 오경보로 센다** (`outcome.ascertainment`가 공개 E17의 정답 칸과 겹친다).
