# 누수 점검 데모 v2 계획

작성: 2026-10-04. v1(2026-10-02~03, `captainjigokdong/leakage-demo`)을 끝낸 뒤, 그 시행착오를 고쳐 다시 하는 실험의 계획이다.

> 이 문서에는 **새 오류 사례 후보의 내용이 없다.** 후보 목록은 봉인 대상이라 저장소와 프로젝트에 평문으로 두지 않는다.

## 1. v2가 무엇인가

- v1과 같은 질문을 다시 검정한다: **점검 스킬이 있으면 에이전트가 설계 결함을 더 잘 잡는가(H1), 처음 보는 결함도 잡는가(H2).**
- v1의 결과("H1 지지 안 됨, H2 지지")는 **그대로 둔다.** v2는 v1 결과를 보고 장치와 기준을 고친 **새 실험**이고, 보고할 때 그렇게 밝힌다.
- 새 저장소에서 한다. v1 저장소는 기록으로 보존하고 더 고치지 않는다.
- 비용: Pro 요금제 안에서만. API 키를 쓰지 않는다. 실행 횟수는 v1과 같은 120회.

## 3. 바뀌는 것

### 3.1 스킬

1. **규칙표 동봉**: 스킬 폴더 안에 규칙표를 읽을 수 있는 형태로 넣고, SKILL.md 첫머리에 위치를 적는다.
2. **판정 근거 표시**: 점검기 출력의 판정마다 "어느 규칙, 어느 값 때문에"를 한 줄로 붙인다.
3. **가정을 드러냄**: 3층 규칙(불확실, 보수적 기본값)을 적용한 곳은 "가정"으로 따로 출력한다. 코딩 지연 일수 같은 값은 규칙표에서 조정할 수 있게 한다.
4. **보고서 세 칸**: 에이전트 보고를 ① 점검기가 차단·경고한 것 ② 에이전트가 추가로 의심하는 것 ③ 가정(참고) 으로 나눈다. ③은 채점하지 않는다.
5. **Q5·Q7 보강**: 2절 9, 10번.
6. **점검기 실행을 필수 첫 단계로** 지침서에 명시한다.

### 3.2 설계서 형식과 데이터

- 형식은 외부 분류(참고문헌) 전체를 보고 넓힌다. 후보 전체가 "설계서 한두 칸을 바꾸는 것"으로 표현되어야 한다.
- 추가할 칸(예): 결과 확인 범위, 분할 방식(무작위·시간 순), 모델 선택·임계값·보정에 쓰는 데이터, 재표본 추출, 사망 처리, 표본 추출 방식.
- 합성 데이터에 필요한 테이블·열을 2단계에서 한 번에 추가하고, 이후에는 테이블을 더 만들지 않는다.

### 3.3 깨끗한 설계서

- v1의 4개를 재사용하지 않고 **새로 8개** 만든다 (설계 유형별 4개).
- 검수 절차 (4단계, 실행 전):
  1. v1에서 드러난 약점을 설계서·규칙표·데이터에서 없앤다.
  2. 스킬 없는 에이전트로 깨끗한 기본 설계서를 한 번 검토시킨다 (실험 실행이 아닌 검수용).
  3. 나온 지적마다 "실제 약점인가"를 판단해, 맞으면 **고친다.** 못 고치는 것만 "정당한 지적" 목록에 넣는다.
  4. 목록을 해시로 잠근다. 목록에 있는 지적은 탐지도 오경보도 아니다. 두 조건에 똑같이 적용한다.
- 넣는 기준은 "에이전트가 지적했는가"가 아니라 "설계서·데이터에서 사실로 확인되는가"다.

### 3.4 채점

- 제출물: 작업 폴더의 `findings.json`. 형식 `[{"target": 항목, "kind": "문제"|"가정"|"점검 불가", "problem": 설명}]`.
- 형식 검사에 실패하면 실행 스크립트가 "파일 형식만 고쳐 다시 제출"을 한 번 요청한다. 두 조건에 같게 적용하고 횟수를 기록한다.
- 주 분석은 v1과 같이 **항목 일치**. 보조 분석은 항목 + 종류.
- 채점기 검증 세트: v1 보고서 119개의 지적 문장에서 뽑는다 (v1 정답표는 이미 공개됨).

### 3.5 가설과 기준 (초안 — 5단계에서 잠금)

| 가설 | 기준 |
|---|---|
| **H1a** 탐지율 | (가) − (나) 탐지율 차이의 95% CI 하한 > 0 (변형 단위 짝지은 부트스트랩 10,000회) |
| **H1b** 오경보(절대) | 깨끗한 변형에서 (가) 오경보 ≤ 보고서당 1건 — v1과 같은 기준 |
| **H1c** 오경보(상대) | 깨끗한 변형에서 (가) − (나) 오경보 차이의 95% CI 상한 < 0 |
| **H2a** 보류 탐지 | 보류 자리에서 (가) − (나) 탐지율 차이의 95% CI 하한 > 0 |
| **H2b** 일반화 격차 | (가)의 공개 탐지율 − 보류 탐지율을 CI와 함께 보고 (기준 없이 기술) |

- 세 기준(H1a·b·c)은 **따로** 판정하고 따로 보고한다. 하나로 묶지 않는다.
- v1에서 (가) 보류 0.783, (나) 보류 0.708이었다. H2a는 v1 기준보다 훨씬 엄격하고, 지지되지 않을 수 있다.

## 4. 보류와 맹검

- **공개 18개** = v1의 E01~E18 전부 (이미 공개됨). 스킬 개발에 쓴다.
- **보류 12개** = 새 후보 30개에서 질문별로 2개씩 스크립트가 무작위 추첨. 추첨은 스킬 동결 뒤에 한다.
  - 후보 배분: Q1 8, Q2 4, Q3 5, Q4 4, Q5 5, Q7 4.
  - 뽑히지 않은 18개는 열지 않고 봉인해 둔다.
- 후보는 문헌에 보고된 오류에서 뽑았고 사례마다 출처가 있다 (9절 참고문헌).
- 후보를 본 세션: 후보 작성 세션(이 문서를 쓴 대화), 1단계 봉인 세션, 2단계 장치 세션, 4단계 이후 세션. **3단계 스킬 세션은 보지 않는다.**
- 주입 코드도 후보 내용을 드러내므로 2단계에서 봉인한다. 스킬 세션이 보는 것은 넓어진 설계서 형식과 v1의 18개뿐이다.
- 보류 사례를 설계서 형식에 맞춰 **조정하지 않는다.** 표현이 안 되는 사례가 나오면 2단계에서 형식을 고친다.

## 6. 실행 규칙 (6단계에서 잠금)

- **채택**: 첫 시도를 채택한다.
- **재실행**: 기계적 실패(인증, 시간 초과, 프로세스 오류)에만. 사유를 기록한다.
- **폐기(오염)**: 다음 둘만 — ① 봉인 파일·정답표·다른 실행의 출력물을 읽음 ② (나) 조건이 스킬·점검 코드를 읽음. 단순한 폴더 탐색은 기록만 한다.
- **허용 도구**: v1과 같은 6개(Read, Glob, Grep, Skill, Write, Bash). 자동 권한 검사가 막은 동작은 우회하지 않는다.
- 작업 폴더는 실행 뒤 지우지 않고 보관한다(커밋하지 않음).

## 7. 사전 점검 목록 (본 실행 전에 한 번에 확인)

1. 하위 에이전트 인증 (세션 환경 상속, root 실행)
2. 허용 도구 6개만 노출되는지
3. (가)에서 스킬이 로드되고 점검기가 실제로 실행되는지, 규칙표 위치를 찾는지
4. (나)의 작업 폴더에 스킬·점검 코드가 없는지
5. 패키지 import (pandas, dateutil 등), 환경 변수(`LEAKCHECK_HOME`은 (가)에만)
6. 변수 확장이 들어간 명령이 권한에 막히지 않는지
7. `findings.json`이 수거되고 형식 검사를 통과하는지
8. 오염 검사가 자기 임시 폴더를 오탐하지 않는지

통과 기준: 조건별 시험 실행 1회에서 8개 모두 충족. 하나라도 실패하면 본 실행을 시작하지 않는다.

## 8. 한계 (미리 적어 둠)

- 후보 사례를 쓴 것도, 스킬을 만드는 것도 같은 모델이다. 다른 사람이 쓴 사례보다 맞히기 쉬울 수 있다.
- 공개 사례가 12개에서 18개로 늘고 v1의 보류 6개도 포함되므로, v2 스킬은 v1 스킬보다 많은 것을 보고 만든다.
- 설계서 형식의 새 칸 자체가 "무엇을 점검해야 하는지"의 단서가 된다. 두 조건이 같은 설계서를 받으므로 비교에는 공평하지만, 절대 탐지율은 높아질 수 있다.
- 합성 데이터, 한 모델, 혼자 하는 실험이라는 v1의 한계는 그대로다.
