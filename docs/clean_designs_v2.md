# 깨끗한 설계서 8개 (v2 4단계 4a)

`designs/clean_v2/`의 8개는 `tools/make_clean_v2.py`가 2b 시험용 기본 설계서(`designs/prereview/`)에 **공통 수정**과 **설계서마다 다른 부분**을 더해 만든다. 손으로 고치지 않는다. 숫자는 `tools/clean_v2_stats.py`로 다시 셀 수 있다 (점검기의 코호트·분할·결과·특징 계산 함수를 쓰고, 판정 함수는 부르지 않는다).

깨끗한 설계서는 "점검기를 통과하는가"가 아니라 **"설계서와 데이터에서 사실로 확인되는 약점이 없는가"**로 판단한다.

## 1. 구성

**같은 유형 4개는 결과 정의·결과 창·tp·코호트·데이터 출처·질문이 같다.** prereview 설계서의 이름 있는 항목(특징·전처리·포함/제외 기준)은 지우거나 이름을 바꾸지 않았다. 오류 사례 48개의 패치가 prereview 설계서를 대상으로 쓰였고(이름으로 칸을 찾는다), 2c의 전제 확인도 그 코호트로 했기 때문이다.

| 설계서 | 분할 | 쓰임새 | 모형 | 더한 특징 (★ = 수상해 보이지만 정당한 항목) |
|---|---|---|---|---|
| aki_a | 시간 순 (2157-07-01, 간격 48h) | 전향 사용 | 로지스틱 | — |
| aki_b | 가족 단위 무작위 30% | 연구용 | 부스팅 | `sbp_slope_24h`, ★ `k_last_6h` |
| aki_c | 시간 순 (2157-01-01, 48h) | 전향 사용 | 부스팅 | `abx_by_tp`, `acei_by_tp`, ★ `n_admissions_to_tp` |
| aki_d | 가족 단위 무작위 30% | 연구용 | 로지스틱 L1 | 결측 표시 단계 `missing_flags`, `hgb_last` |
| readmit_a | 시간 순 (2157-01-01, 30d) | 전향 사용 | 로지스틱 | — |
| readmit_b | 가족 단위 무작위 30% | 연구용 | 부스팅 | `n_clinic_365d`, ★ `prior_dx_group` |
| readmit_c | 시간 순 (2156-07-01, 30d) | 전향 사용 | 부스팅 | `dc_diuretic`, ★ `prior_cr_last` |
| readmit_d | 가족 단위 무작위 30% | 연구용 | 로지스틱 L1 | 결측 표시 단계 `missing_flags`, `k_last` |

- 전향 사용을 목적으로 하면서 무작위 분할을 하면 시간에 따른 변화(측정법·코드 체계·ICU 비율)를 평가하지 못한다 (예비 검수 B10, 점검기 `S.temporal_deploy`). 그래서 전향 사용 설계서는 시간 순으로 나누고, 무작위 분할 설계서는 쓰임새를 연구용(전향 사용 전의 내부 검증)으로 둔다.
- 분할 칸(`split.*`)을 바꾸는 사례는 가족 무작위 분할 바탕에만 배치한다 (아래 5절: 시간 순 바탕에서는 E05의 수치 차이가 1~2).

## 2. 공통 수정과 반영한 지적

| 유형 | 칸 | 수정 | 반영한 지적 |
|---|---|---|---|
| 동적 | `question`, `outcome.description` | 결과를 "퇴원 전 원내 사건: AKI 또는 원내 사망"으로 쓰고, 창 안 퇴원·측정 없음의 처리와 병동별 보고를 적음 | R2·B25, R4 |
| 동적 | `outcome.description` | 시각 기준을 한 규칙으로: "tp에 아직 보고되지 않았고 tp+48시간까지 채취된 크레아티닌으로 사건을 판정한다. 보고가 창 뒤여도 채취가 창 안이면 센다" | 승인 A 확인 4 |
| 동적 | `outcome.censoring.end_of_data` | `exclude_incomplete` | R5 (`O.end_of_data`) |
| 동적 | `outcome.pending_at_tp` | `count_as_outcome` | B27, 점검기 `C.pending` |
| 동적·고정 | `features.cr_last.assessment.method` | "측정법을 함께 넣는다" 모순 문장을 지우고, 섞인 채로 쓰며 측정법을 특징으로 넣지 않는 이유를 적음 | R1·B22 (B11) |
| 고정 | `preprocessing.*.fit_scope` | `train_fold` (조율 폴드마다 다시 맞춤) | 점검기 `F.fold_refit` (B17과 같은 원리) |
| 고정 | `outcome.description` | `definition=next_admission`은 창 안 같은 사람의 입원을 모두 본다고 적음 | R6 |
| 전향 사용 4개 | `split` | 시간 순 분할 | B10 |

2b 예비 검수에서 이미 고친 지적(B1~B9, B11~B19, B21, B23, B24, B26, B27)은 prereview 설계서에 들어 있어 8개 모두에 그대로 있다.

## 3. 점검기 결과 (승인 A, 2026-10-05)

설계서만 / 본 데이터와 함께 돌린 결과가 같았다.

| 설계서 | 차단 | 경고 | 가정 |
|---|---|---|---|
| aki_a~d | 0 | Q7 `data_source.death_source` (`docs/known_issues_v2.md` K2) | `A.family_missing` ×2 (`split.key`, `model.tuning.cv_key`) |
| readmit_a, c, d | 0 | 0 | `A.family_missing` ×2, `A.episode_last`, `A.outside_sites` |
| readmit_b | 0 | Q4 `features.n_clinic_365d` (K1, 사실 아님 → 그대로 둠) | 같음 |

- readmit_b의 외래 방문 수는 tp 뒤 정보가 섞이지 않음을 확인했다: 창 안 방문 1,256건(추적 904, 정기 352) 중 tp 뒤 방문 0건, 창 안 추적 외래는 모두 이전 입원의 추적이다 (K1). 경고를 없애려고 설계서를 고치지 않는다 (2026-10-05 사용자 결정). 이 경고를 옮겨 적으면 오경보다.
- 점검기 출력을 본 뒤 빼거나 바꾼 항목은 없다 (readmit_b의 필터를 넣었다가 되돌린 것 하나).
- 공개 18개 중 패치 대상 칸이 점검기 **경고** 칸과 같은 사례는 없다. **가정** 칸과 같은 사례는 E05·E06·E07(`split.key`)과 E18(`outcome.ascertainment.scope.sites`)이다 (5단계로 넘김).

## 4. 수상해 보이지만 정당한 항목 4개 (조건 C)

각 항목은 데이터 설명서로 "값이 알려지는 때"를 확인하고, 본 데이터에서 **(1) 점검기 특징 계산의 확인 가능 시각이 tp 뒤인 행 수**와 **(2) 원자료로 따로 고른 행의 '알려지는 시각' − tp의 최댓값**을 셌다 (`python -m tools.clean_v2_stats --star`). 수상해 보이는 이유는 정답표에 "결함 아님"으로 적고, 에이전트가 지적하면 오경보다. 검수에서 사실로 확인되는 약점이 나오면 그 항목을 바꾼다.

| 설계서 · 항목 | 수상해 보이는 이유 | 설명서 근거 | 데이터 확인 |
|---|---|---|---|
| aki_b · `k_last_6h` (칼륨, 창 (tp−6h, tp], 보고 시각) | 창이 tp에 바짝 붙어 있다 | `labs.report_time`: 보고 시에 알려진다 | 25,832행 중 값이 있는 행 4,897. 점검기 확인 시각 > tp 0행. 쓰인 원자료 4,907행의 보고 시각 − tp 최댓값 0시간, 모두 tp 전 채취 |
| aki_c · `n_admissions_to_tp` (같은 등록 번호에서 입원 시각 ≤ tp인 입원 수) | 이번 입원이 포함되고 창 끝이 tp다 | `admissions.admit_time`: 입원 시에 알려진다 | 모든 행(25,832)에 이번 입원이 1로 들어감 (상수 이동이라 정보 누수 아님). 점검기 확인 시각 > tp 0행. 쓰인 원자료 38,828행의 입원 시각 − tp 최댓값 −24시간. tp에 진행 중인 다른 입원 0 |
| readmit_b · `prior_dx_group` (이전 입원 주진단, 코딩 완료 ≤ tp, 범주형, 학습 폴드 one-hot) | 진단 코드는 퇴원 뒤 코딩된다 (E01 같은 결함과 비슷해 보임). E09 패치가 더하는 특징과도 비슷하다 | `diagnoses.icd_code`·`coded_time`: 코딩 완료 시 알려진다 | 6,706행 중 값이 있는 행 1,998, 범주 26종. 점검기 확인 시각 > tp 0행. 쓰인 원자료 2,952행의 코딩 완료 − tp 최댓값 −0.25시간. 이전 입원 주진단 중 코딩이 tp 뒤에 끝나 쓰이지 않은 것 3,990건 (창이 제대로 거름) |
| readmit_c · `prior_cr_last` (다른 입원의 마지막 크레아티닌, 보고 ≤ tp) | 다른 입원의 검사를 tp까지 가져온다 | `labs.report_time`: 보고 시에 알려진다 | 6,706행 중 값이 있는 행 2,240. 점검기 확인 시각 > tp 0행. 쓰인 원자료 14,019행의 보고 시각 − tp 최댓값 −29.95시간. 보고가 tp 뒤라 쓰이지 않은 다른 입원 값 14,388건 (뒤 입원 포함) |

- E09 검토 (2c에서 넘김): 고정 B에 진단 코드 범주형 특징(`prior_dx_group`)을 학습 폴드 one-hot으로 넣었다. E09 패치가 더하는 이름 `prior_dx_main`은 쓰지 않았다 (같은 이름이면 패치가 실패한다). 그래서 E09가 들어간 변형만 진단 코드 범주형 특징을 가진 것이 아니게 된다.
