# 설계 누수 점검

**규칙표: 이 스킬 폴더의 `rules.md`.** 점검기가 쓰는 규칙(값마다 언제 알려지는가, 분할 위계, 대리 기록, 확인 강도 층, 가정, 판정 규칙 번호)이 모두 들어 있다. 같은 내용을 `python3 <이 스킬 폴더>/scripts/run_check.py --rules`로도 볼 수 있다. 규칙을 찾으러 다른 곳을 뒤지지 않는다.

이 스킬 폴더에 있는 파일은 세 개뿐이다: `SKILL.md`(이 파일), `rules.md`(규칙표), `scripts/run_check.py`(점검기 실행기).

## 1. 필수 첫 단계: 점검기 실행

설계서를 받으면 **데이터 처리, 탐색, 모델링보다 먼저** 아래 명령을 그대로 실행한다. 이 단계를 건너뛰거나 뒤로 미루지 않는다.

```
python3 <이 스킬 폴더>/scripts/run_check.py <설계서 파일> --data <데이터 폴더>
```

- `<이 스킬 폴더>`는 이 SKILL.md가 있는 폴더다. `<설계서 파일>`, `<데이터 폴더>`는 작업에서 받은 것을 쓴다. 데이터 폴더가 있으면 항상 `--data`로 준다.
- 점검기는 결과를 화면에 출력하고, 같은 내용을 JSON 파일로도 저장한다 (저장한 파일 이름이 출력에 나온다).
- 출력 마지막 줄이 `종료 코드 n = 뜻`이다: 0 차단 없음, 1 차단 있음, 2 점검 불가. 종료 코드를 따로 확인하는 명령은 쓰지 않는다.
- 점검기 실행에 실패하면(점검 불가) 메시지를 그대로 보고에 옮긴다. 점검기를 다른 방법으로 다시 만들거나 판정을 손으로 흉내 내지 않는다.
- 셸 명령은 위 형태처럼 단순하게 쓴다. 여러 줄 입력(heredoc), 명령 치환, 특수 변수(종료 코드 등), `find -exec`는 권한 규칙에 막힐 수 있다. 데이터를 더 확인하고 싶으면 스크립트 파일을 만들어 `python3 <파일>`로 실행한다.

## 2. 점검기 출력 읽기

판정마다 세 줄이 나온다: `[판정] 질문 · 대상` / `근거: 규칙 <번호>(<규칙 내용>) · 값: <어떤 값 때문에>` / `설명:`. 규칙 번호의 뜻은 `rules.md` 7절에 있다.

| 판정 | 뜻 | 보고 |
|---|---|---|
| 차단 | 원리 위반이 확정됨 | ① 점검기 판정 |
| 경고 | 사람이 판단해야 함 | ① 점검기 판정 |
| 점검 불가 | 규칙표에 없거나 출처 불명이라 확인하지 못함 | ① 점검기 판정 (점검 불가로 표시) |
| 가정 | 3층 규칙(보수적 기본값)을 쓴 곳. 판정이 아님 | ③ 가정 (참고) |
| 통과 · 기록 | 위반 없음 / Q6 시도 기록 | 보고하지 않음 (근거 확인용) |

판정을 직접 바꾸거나 빼지 않는다. 판정이 사실과 다르다고 보이면 그대로 두고, 이유를 ②에 따로 적는다.

## 3. 점검 원리 (Q1~Q7)

점검은 사례 목록이 아니라 세 가지 비교로 한다. 규칙표는 각 값이 "언제 알려지는가"만 정하고, 그 값을 쓸 수 있는지는 설계의 예측 시점 tₚ가 정한다.

- **Q1 가용 시점**: 모든 특징의 *확인 가능 시각*(값이 생긴 시각이 아니라 알려진 시각)이 tₚ 이전이어야 한다.
- **Q2 독립 단위**: 분할 묶음(교차검증 묶음, 대체 키 포함)은 선언된 독립 단위 이상이고, 개체 단위(사람) 이상이어야 한다.
- **Q3 적합 범위**: 데이터에서 추정하는 모든 것(대치, 척도화, 인코딩, 선택, 재표본 추출, 임계값, 보정)은 학습 부분에서만 정한다. 성능은 그 결정에 쓰지 않은 부분에서 계산한다.
- **Q4 결과 출처**: 결과를 정한 행·결과 창과 겹치는 특징, 결과를 정하는 과정이 남긴 기록(대리 기록)을 특징으로 쓰지 않는다.
- **Q5 선택 시점**: 누가 포함되는지(포함·제외 기준, 표본 추출, 단위마다 고르는 행, 결과 창 안 사건으로 빼기)는 기준 시점 이전 정보로만 정한다.
- **Q6 다중 시도**: 설계·모델을 몇 번 시도했는지 기록한다.
- **Q7 결과 확인 균질성**: 결과를 확인하는 강도(측정 빈도, 확인 범위, 등록 번호 연결, 측정법 변경, 사망 출처)가 층마다 같거나, 층별로 다뤄야 한다.

## 4. 점검기 다음: 추가로 의심할 것 (②)

점검기는 아래 칸을 판정에 쓰지 않는다. 설계서에 이 칸이 있으면 직접 읽고, 위 원리에 비춰 문제가 있으면 ②에 적는다.

- 자유 서술: `question`, `notes`, 각 항목의 `description`, `intended_use.deployment_start`, `intended_use.setting`, `outcome.definition_source`, `outcome.reference.agg`, `outcome.ascertainment.method`, `outcome.ascertainment.min_followup`, `outcome.history`의 내용, `model.family`, `model.tuning.method`, 모형 결정 칸의 `method`·`metric`
- 판정 원리가 없는 칸: `evaluation.metrics`, `evaluation.subgroups`, `evaluation.calibration_reported`, `analysis.missing_data.method`, `analysis.missing_data.drop_rows_when`, `cohort.sampling.by`·`fraction`·`ratio`, `split.by_site`, `data_source.study_period`, `outcome.ascertainment.scope.settings`, 특징의 `assessment`, `age_reference`, `version_order`, `outcome.reference.compare_to`, `outcome.planned`, `outcome.planned_by`
- 설계서의 서술과 실제 칸 값이 서로 맞는지
- 점검기가 "점검 불가"로 남긴 항목

②는 근거(설계서의 어느 칸, 데이터의 어떤 사실)를 함께 적는다. 근거 없이 "~일 수도 있다"는 적지 않는다.

## 5. 보고

보고는 세 칸으로 나눈다.

1. **① 점검기가 차단·경고·점검 불가로 낸 것**: 판정마다 대상(설계서 경로), 질문, 근거 줄, 수정안.
2. **② 추가로 의심하는 것**: 4절에서 찾은 것. 대상, 해당 원리(Q), 근거, 수정안.
3. **③ 가정 (참고)**: 점검기가 가정으로 낸 것을 그대로.

맨 앞에 결론 한 줄(차단 있음/없음, 경고 수)을 쓴다. 통과와 Q6 기록은 보고하지 않는다.

**수정안은 규칙표로 확인한다**: 수정안(특히 ②의 수정안)을 내기 전에 `rules.md`에서 그 수정이 다른 규칙에 걸리지 않는지 확인한다 (값이 언제 알려지는가, 분할 위계, 가정). 확실하지 않으면 고친 설계서로 점검기를 다시 돌려 확인한다.

**제출 형식**: 작업 지시가 제출 파일과 형식을 정하면 그것을 따른다. 형식에 `kind` 칸이 있으면 ①과 ②는 `문제`, ③은 `가정`, 점검기의 점검 불가는 `점검 불가`로 적는다 (점검기 출력의 `kind` 칸을 그대로 옮기면 된다). 대상(`target`)은 점검기와 같은 설계서 경로로 적는다 (예: `features.<특징 이름>`, `cohort.exclusion.<기준 이름>`, `preprocessing.<단계 이름>`, `split.key`, `outcome.<칸>`).

## 6. 진행 규칙

- 차단이 하나라도 있으면 모델을 학습하거나 성능을 계산하지 않는다.
- 차단이 없으면 `--card`를 더해 결정 카드(표본 수, 결과율만)를 만들어 사람에게 보여 준다. 사람이 승인해 잠그기 전에는 성능을 계산하지 않는다.
- 규칙표, 점검기, 판정 기준을 고치거나 우회하지 않는다. 점검기의 위치나 소스를 찾아 읽지 않는다. 규칙이 틀렸다고 보이면 근거와 함께 ②에 보고한다.
